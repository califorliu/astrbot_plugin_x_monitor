# astrbot_plugin_x_monitor

监控 X（原 Twitter）账号并把新帖转发到会话。面向 SnowLuma / OneBot v11（aiocqhttp）接入层。

## 功能

| # | 能力 | 说明 |
|---|---|---|
| 1 | 多账号监控 | `/x订阅` 增删、按群独立列表与游标，**首次订阅不补发历史** |
| 2 | 原文与翻译 | 复用 AstrBot 已配置的模型，**不需要额外 API key**；带超时预算与熔断 |
| 3 | 图片与视频 | 原图直链下载到本地有界缓存；合并转发时自动降到 `large` 以免 payload 过大 |
| 4 | 多类型发送 | 合并转发（节点昵称可自定义）/ 普通消息链，自动降级；视频独立另发 |
| 5 | 免打扰时段 | 时段内只入队不发送，时段外按速率逐条补发；超积压上限丢弃最旧并汇总告知 |
| 6 | 多源降级 | FxTwitter API → FxTwitter RSS → 自建 RSSHub/Nitter 实例池；熔断、故障转移、按账号标注生效源 |
| 7 | 图库联动 | 可选（默认关）：推文照片归档进 `astrbot_plugin_image_pool`，tag = 该订阅的自定义昵称；对端缺失/停用/旧版本都不影响推送 |

## 安装

1. 把 `astrbot_plugin_x_monitor/` 放到 AstrBot 的 `data/plugins/` 下
2. 重启 AstrBot 或在 WebUI 插件页重载
3. 依赖：`httpx[http2]`（AstrBot 通常已自带）

## 快速开始

```
# 1. 先拿到自己的 ID 与群号
/x在哪

# 2. 在 WebUI 插件配置里填「全局管理员」= 上一步的 UID
#    （留空则谁都无权管理，插件默认不可用）

# 3. 订阅一个账号（昵称可选，但填了才会同步到图库）
/x订阅 elonmusk 马斯克

# 4. 自检发送通道
/x测试
```

| `/x推送 开\|关 [handle]` | 本群管理员 | 开关本群（或单个）订阅的推送 |

| `/x解析 <url>` | 按群模式 | 解析一条 X 链接并就地回显 |
| `/x测试 [handle]` | 所有人 | 发送一条链路自检消息；带 handle 时会用该订阅的昵称，**正文里直接告诉你节点昵称会显示成什么** |

### 触发方式

插件指令**不需要带前缀**。AstrBot 的 `wake_prefix`（例如 `/`）负责唤醒，唤醒后框架再匹配插件指令，
`WakingCheckStage` 已把前缀从 `message_str` 剥掉。因此所有指令都用 `@filter.command` 注册。

> 刻意**没有**用 `@filter.regex` 做被动链接识别：`RegexFilter` 不受唤醒门控，
> 会在所有消息上触发，从而与共用同一 OneBot 接入层的其它 bot 抢答。

## WebUI 管理页

在 AstrBot 插件详情页里打开「管理」页（`pages/manage/`），提供三个标签页：

| 标签 | 内容 |
|---|---|
| **订阅矩阵** | 行 = 监控账号，列 = 群，**勾选即订阅**；下方是订阅明细（逐条改昵称 / 推送开关 / 仅媒体）、每群免打扰时段、以及发送测试与回放按钮 |
| **运行状态** | 订阅数 / 账号数 / 已收录推文 / 待投递队列 / 媒体缓存占用 / 最近失败次数与原因；每个账号的基线与水位时间 |
| **全局配置** | 由插件自带的 `_conf_schema.json` **驱动渲染**，改哪项提交哪项，后端逐项校验，**任一项不合法则整体不落盘** |

**选群：不会猜平台前缀。** 页面上的群选择器只有两种来源：

- **已知群下拉** —— 来自"登记过的会话 ∪ 有订阅的群 ∪ 设过免打扰的群"，值是**完整 umo**
- **手动输入** —— 选一个**平台实例**（下拉，来自 AstrBot 真实的 `platform_manager.platform_insts`）+ 填群号，页面实时预览将写入的完整 umo

裸群号（如 `123456789`）交给**后端**在已知 umo 里按群号**唯一匹配**；匹配不到会明确告诉你"先去那个群执行 `/x在哪`"，多个平台命中则报歧义让你选完整 umo。

> ⚠️ **umo 第一段是「平台实例 id」，不是适配器名。** 它是你在 AstrBot 里给这个适配器实例起的名字（可以叫「mybot」），而 `aiocqhttp` 只是**适配器类型名**。
> 写错不会报格式错误，而是在发送时才失败：`cannot find platform for session ...`。
> 所以 `resolve_umo` 会拿它跟真实平台实例表比对，不存在就当场拒绝并列出可用 id。`/x在哪` 也会把平台实例 id 单独标出来。

**安全假设（页面上也写了这句话）**：能登录 Dashboard 的人本就受信任，因此该页等同于
**全局管理员面**，这里**不做**额外的插件级鉴权。技能文档明确建议不要把 Dashboard 用户名
映射到聊天用户 ID，而是直接声明这个假设。

**版本要求**：Plugin Pages 需要 AstrBot **≥ v4.24.1**。更旧的版本上插件照常安装与工作，
只是会自动跳过路由注册并打一条 warning（`metadata.yaml` 里刻意**没有**写 `>=4.24.1`，
否则会把只想要命令功能的用户挡在门外）。

**几个实现约束**（决定了页面怎么写）：

- iframe 无 `allow-modals`，`alert` / `confirm` / `prompt` 会**静默失效** → 自绘 toast 与 Promise 化 modal
- iframe 无 `allow-same-origin`，拿不到 Dashboard cookie → 一切数据走 bridge，不直接 `fetch`
- 路由带插件名前缀（`/astrbot_plugin_x_monitor/overview`），而页面侧 endpoint **不能带**（`bridge.apiGet("overview")`）
- 用户数据一律用 DOM 构造写入，不拼 `innerHTML`

**装完看不到页面时，按这个顺序查**（源码确认：AstrBot 的页面服务在跳过非法目录时
**一行日志都不打**，所以"日志里没线索"是正常的）：

1. **先看插件启动日志**，这三条能直接把问题域切一半：
   - `[x_monitor] 未找到 WebUI 页面文件 …` → 插件包里没有 `pages/`，是**打包不完整**
   - `[x_monitor] 当前 AstrBot 不支持 Plugin Pages` → 内核 < v4.24.1
   - `[x_monitor] WebUI 管理页就绪：pages/manage/index.html + N 条路由` → 后端已就绪，问题在前端
2. **Ctrl+F5 整页硬刷新**。Dashboard 侧边栏列表由 `usePluginSidebarItems` 的模块级
   `initialFetched` 缓存，**一次前端会话只拉取一次** —— 只重载插件、或只按 F5，都可能看不到。
3. **直接问后端**：`GET /api/v1/plugins?name=astrbot_plugin_x_monitor`，看返回里的 `pages` 数组。
   空 = 文件系统 / 路径问题；非空 = 前端缓存或插件未启用。
4. 确认目录层级就是 `pages/manage/index.html`（`index.html` 文件名必须**精确**）。
   `metadata.yaml` 里**不需要**也**不应该**声明 `pages` / `views` —— 框架不消费这两个字段
   （`pages` 只被写进 `StarMetadata` 后无人读取，`views` 在 v4.26.4 中甚至不存在）。

> 另外：**新增 `register_web_api` 路由后必须重载插件**（注册只发生在 `__init__`，
> `registered_web_apis` 从不被清理）；只改静态资源（`app.js` / `style.css`）才只需要刷新页面。

## 权限模型

沿用 `astrbot_plugin_image_pool` 的既有模型，**不借道 AstrBot 全局管理员**。

| 群模式 | 订阅（增删本群监控目标） | 查看（列表 / 状态 / 解析） |
|---|---|---|
| `whitelist` 白名单群 | 全员 | 全员 |
| `readonly` 只读群 | 仅管理员 | 全员 |
| `none` 未配置（**默认**） | 仅管理员 | 仅管理员 |

- `plugin_admins`：全局管理员，可管整库、改群模式、授权。**默认空 = 谁都无权管理**（安全默认）
- `group_admins`：`群号:UID`，只能管本群订阅，可改本群昵称与免打扰
- 所有校验在 handler 内部完成（不是 `@filter.permission_type`），因为 AstrBot 没有「群管理员」这种粒度

## 免打扰时段

```
/x免打扰 23:00-08:00          # 跨天，单段
/x免打扰 12:30-13:30, 23:00-08:00   # 多段
/x免打扰 关
```

**免打扰是按群（按会话）的**：群管理员改的是自己群的时段，不会波及其它群。
群级设置存在 `groups` 表里；没有该群的行时才回落到全局配置的 `dnd_enabled` / `dnd_ranges`。

架构上**拉取与投递解耦**：时段内照常抓取、照常存库、照常翻译，只是不进发送环节。
排空器逐个会话判断，处于时段的会话跳过（消息留在队列），其它会话照常发送。
时段结束后按 `dnd_drain_rate`（默认 5 条/分钟）逐条补发，间隔以"上次发送时刻"为基准计算，
跨批次同样成立，并叠加随机抖动。

- 积压超 `dnd_backlog_limit` 时**按群**丢弃最旧的，并向该群发送汇总告知（绝不静默丢弃）；
  通知带 `backlog_notify_cooldown_minutes` 冷却（默认 30 分钟），否则队列持续超限时会刷屏
- **积压裁剪在免打扰期间也执行**，否则一个长时段就能把队列撑爆
- `/x免打扰 关` 的语义是**清除本群覆盖行、回落到全局默认**（而不是留下一条"显式关闭"的记录）——
  否则这个群会**永久**不再继承全局默认值，且没有任何恢复入口。命令回复会告诉你当前实际生效的设置
- `dnd_timezone` 默认 `Asia/Shanghai`。**Docker 容器通常是 UTC，务必显式设置**，否则时段会整体偏移 8 小时

## 验证生产链路（不需要自己发帖）

订阅成功后不必等真实推文，也不必用自己的账号发帖：

```
/x测试 elonmusk      # 1. 先确认发送通道通，并看到"节点昵称会显示成什么"
/x补发 elonmusk 3    # 2. 回放该账号最近 3 条真实推文，走完整链路
```

`/x补发` 会完整走一遍 **下载图片 → 翻译 → 合并转发（含自定义昵称）→ 逐级降级**，
因此一次就能验证：图片能不能收到、翻译有没有生效、合并转发的节点昵称是否正确显示。

它刻意**不推进水位、不写投递记录**，所以：

- 可以反复执行，不会污染去重状态
- 不会与后续真实推送重复
- 不会打乱正常推送节奏

`/x测试 <handle>` 的正文里会写明节点昵称的来源（本群自定义 / 推主名 / 兜底值），
配合 `/x昵称 <handle> <昵称>` 可以立刻对比自定义昵称是否生效。

## 仅媒体订阅

```
/x仅媒体 elonmusk 开     # 该订阅只推含图片 / 视频 / GIF 的帖子
/x仅媒体 elonmusk 关     # 恢复为拉取全部原创帖（默认）
```

**这是按订阅的开关**，不是全局配置：同一个账号可以对 A 群只推媒体、对 B 群推全部。
默认关闭，即"拉取全部原创帖"。

**判定口径**：推文的 `media.all` 存在且非空即算含媒体，只认 `photo` / `video` / `gif`。

- `media.external`（YouTube 等**外链卡片**）**不算** —— 那是链接预览，不是帖子自带的媒体，
  否则"带链接的纯文字帖"也会被当成含媒体
- `media.mosaic` 的 `mosaic_photo` 是对已有图片的合成视图，不在 `media.all` 里，天然不计入
- 纯媒体帖的 `text` 可以为空字符串，这类当然算含媒体

**与其它过滤的关系**：`media_only` 是**额外的收窄条件**，转推 / 回复 / 引用的过滤依然先生效。
即"含媒体的原创帖"。

**水位语义**：被跳过的纯文字帖**不会补发** —— 即使之后关掉这个开关也不回溯。
这与"首次订阅不补发历史"是同一套语义，避免出现"开关一关就倒灌一堆旧帖"。

`/x补发` 同样遵守该开关（订阅开了仅媒体，回放也只回放带媒体的帖子）。

| 键 | 默认 | 说明 |
|---|---|---|
| `plugin_admins` / `group_admins` | `[]` | 管理员名单，见上 |

| `forward_image_quality` | `large` | 合并转发时的画质（避免原图撑爆 payload） |

## 数据与存储

```
data/plugin_data/astrbot_plugin_x_monitor/
├─ xmonitor.sqlite3        authors / edges / posts / deliveries / groups / meta
└─ media/<sha256>.<ext>    有界媒体缓存（配额 + TTL + LRU 淘汰）
```

**升级会自动补列**：插件目录更新会整体替换，但数据目录不会。因此启动时按
`PRAGMA table_info` 探测缺列并 `ALTER TABLE ADD COLUMN`（如 `edges.media_only`、
`posts.has_media`），**已有订阅数据不会丢**，也不需要手工迁移。

四条正确性不变量（都有离线测试守着）：

1. `UNIQUE(edge_id, post_id)` —— 结构上杜绝同一会话重复推送
2. `edges.enqueued_ts` 只增不减 —— 单调水位3. 抓取失败**不写** `last_seen_ts`、**不置** `baseline_ready` —— 区分「网络失败」与「确实没有新帖」
4. 首次订阅建立基线，不补发历史

一轮抓取的提交是**单个事务**：写 posts → 为每条边入队 → 推进两条水位。任一环节失败整体回滚，
下一轮用同一个 `since` 重新拉到，既不会漏也不会重。

## 数据源

默认是一条**有序降级链**，按顺序尝试、谁先成功就用谁（`fetch_chain` 可改）：

```
L1 fxtwitter      FxTwitter / FxEmbed V2 API   https://api.fxtwitter.com   免 key，功能最全
L2 fxtwitter_rss  https://fxtwitter.com/{h}/feed.xml                      同服务的 RSS 面（实测含图片/视频）
L3 rsshub         自建 RSSHub / Nitter 实例池   需在 rsshub_instances 里填  多实例故障转移
```

几个刻意的语义选择（都有离线断言守着）：

- **`ok=False` 才降级**。降级判定只在**层与层之间**：某一层给出"没有新帖"就是结论，
  不会再去问下一层（否则第二层只能给出更弱的结论，反而把质量拉低）。
  同一个源内部的多个 URL 是"同一份数据的不同入口"，由该源自己决定怎么试完。
- **"解析不出来" ≠ "没有新帖"**。200 但返回 HTML 验证页（Nitter 类镜像常见）会被当成
  **该源不可用**并切换；如果误判成"没有新帖"，水位就会静默停摆。
  同理，FxTwitter 返回 `200` + 空 `results` 且**没有 `cursor`** 时也按"源不可用"处理——
  真正的"无新帖"信号是 HTTP 204，把 200+空数组当无新帖是自建反代下永久漏推的入口。
- **熔断是"延后"，不是"每轮探活"**。某源连续失败（`provider_failover_threshold`，默认 1 次）
  后被挪到队尾并冷却 `provider_cooldown_sec`（默认 600 秒）。因为**找到可用源就立刻返回**，
  冷却期内若还有别的健康源，它不会被试到；它会在两种情况下重新被试到：
  **冷却到期回到原顺位**，或者**其余源全部失败时的兜底轮次**。
  阈值与冷却时间都是**即时生效**的配置，改完不用重载。
- **404 不等于源坏了**。`/x订阅` 打错一个字母只会记一笔 `not_found`，**不会**把健康源
  冷却 600 秒拖累其它账号；连续多次 404 后会拿 `probe_handle`（默认 `X`，必然存在）探一次，
  **只有探针账号也拿不到数据**才判定"这个源坏了"并冷却。只有网络/解析失败才进 `failures` 计数。
  这样"几个账号被删/改名"不会冤枉健康源，而"base 配错、对谁都 404"仍能被降级。
- **按账号记生效源**。`/x状态` 显示数据源链、当前源与降级告警；WebUI 账号表也显示每个账号
  当前由哪个源供数，总览里还有"数据源明细"（成功/失败/账号不存在/源探测失败/已熔断）。
  `/x源`（仅全局管理员）可看每个源的熔断状态与 RSSHub 各实例健康，
  `探测` 会拿 `probe_handle` 对每个源做一次独立可用性检查（**不污染主链计数**），
  `源名` 可把某个源临时提到队首（**只对下一次轮询生效**；订阅解析与回放既不吃掉它也不受它影响）。

FxTwitter V2 的实测行为（轮询器就是按这些写的）：

- 增量拉取用 `?since=<秒级时间戳>`；**无新帖返回 HTTP 204**（靠状态码判断，204 时不要解析 body）
- `count` 参数**完全无效**（页大小固定 20）
- `since_id` **被静默忽略** —— 绝不能用
- `with_replies=true` 会插入被回复的原帖并**产生重复 id**，因此解析后按 `post_id` 去重
- 判断帖子类型：转推 `reposted_by` / 回复 `replying_to` / 引用 `quote`（`tombstone` 视为原创）
- `replying_to` 是对象，父帖 id 在 **`status`** 字段（对象里没有 `id`）

### RSS 面（L2/L3）实测与已知短板

开发期拿真实 `fxtwitter.com/<handle>/feed.xml`（90 个 `<item>`）逐项测过；
那份真实语料**不随包发布**，仓库里随包的是按同一字段形状构造的合成样本
`tests/fixtures/fxtwitter_feed_sample.xml`（5 条，内容全虚）：

| 项 | 实测 |
|---|---|
| 条目数 / 时间跨度 | **90 条**（L1 是固定 20 条/页，所以 L2 的补漏窗口约 4.5 倍） |
| 转推 | **54/90 条的 `<link>` 指向别人** —— 该 feed 是"含转推的时间线"，插件据 `<link>` 判定作者并补出 `reposted_by`，`filter_reposts` 因此在 L2 上照常生效 |
| 引用 | 50/90 条带 `<blockquote>`（被引用帖的正文），已拆进 `quote` 字段，**不混进正文** |
| 媒体 | **34/90 条含媒体**：图片 15 条 + `video/mp4` 19 条（另有 2 条的 `<enclosure>` 是 twimg 的 `/card_img/` **链接卡片预览图**，按 L1 的 `media.external` 口径**不算**帖子媒体）。视频会被映射成 `media.all` 里的 `video`，所以「仅媒体」订阅在 L2 上不会丢视频帖 |
| 正文 | `description` 100% 走 CDATA；`<a>Media</a>` 这类附件占位锚文本会被剔除（否则 20/90 条会多出一行 "Media"）；与附件同形（正文恰为 `Media` + 媒体直链）的用户帖子会被一并剔除，靠 `<title>` 兜回 |
| 日期 | 只有秒级 `pubDate`；整份 feed 一条日期都没有时判该源不可用（绝不拿"抓取时刻"当时间戳，那会把水位抬到未来造成永久漏推） |
| `lang` | **没有这个字段**。插件用廉价启发式补（假名→ja、谚文→ko、汉字为主→zh、拉丁为主→en），让 `skip_langs` 在 L2 上也能生效；**全汉字无假名的日文会被判成 zh**（字符层面无法与中文区分） |
| 显示名 | 转推的原作者显示名 RSS 里拿不到（只有 handle），对应条目会显示成 `other_author (@other_author)` |
| XML 容错 | 第三方源常输出 HTML 命名实体（`&nbsp;`）、裸 `&`、未声明 `xmlns:media`；解析失败时会做一次修复再试，避免一条小瑕疵让整份 feed 判死（修复器**不会**改动本来就正确的 `&amp;` 等预定义实体） |
| 请求量 | "无新帖"要试完三个面（`/feed.xml`、`/feed`、`/rss`）才能下结论——**正确性优先**：曾经为了省一个请求改成"第一个面成功即返回"，结果空面会遮住有内容的面，首轮还会把水位设成 now 造成永久漏推。只有**真的出了条目**的面才会被记成"下次首选"，所以安静账号仍是每轮 3 个请求 |

> **L2 的两个真实短板**（不是 bug，是数据源本身的限制）：
> 1. **拿不到回复帖**。实测该 feed 与"默认时间线"在采样窗口内 id 完全一致（19/19），
>    且不含 `with_replies=true` 独有的 id（0/9）；但 RSS 层面**无法区分引用与回复**，
>    所以严格说只能讲"采样窗口内不含回复"，不能保证永远不含。开了 `include_replies=true`
>    的用户在切到 L2 后可能少收一部分内容。
> 2. **视频只有一档 mp4**（没有 L1 的 `formats[]` 码率选择）；`send_video=false` 时视频帖仍会被
>    计为"含媒体"（口径与 L1 一致），但**只发文字与链接**，不发画面。

## 已知限制

- **合并转发依赖协议端**：AstrBot 会把 `name` → `nickname` 正确透传，但节点昵称最终是否按预期显示，
  取决于 NapCat / Lagrange / go-cqhttp 的实现。**请在真实环境下目视确认一次。**
- **只声明支持 `aiocqhttp`**：非 OneBot 平台对 `Nodes` 没有明确降级路径，插件会自动退回普通消息链。
- **视频不放进合并转发节点**，始终独立另发。
- 图片放入 `Nodes` 会被 `Node.to_dict()` 转成 base64 内联，因此合并转发的 payload 约为原图的 1.34 倍。
  插件按 `max_forward_payload_mb` 自动拆批，但**画质档位仍是最有效的控制手段**。
- 与 `astrbot_plugin_image_pool` 的自动入库联动**已实现**（v1.4.0，默认关闭，需图库 v1.7.0+）：
  只归档照片、只归档设置了自定义昵称的订阅、X 归档图不归属任何群（仅图库全局管理员可管理）。
  X 归档图在图库里记为 `source=x`，而图库默认的保留期清理只处理 `source=auto`，
  所以它们**不会被自动淘汰、也不计入 `max_pool_mb` 容量统计** —— 目录只涨不缩，请自行留意磁盘。
- **入库失败是有损的，且没有自动补归档入口**：水位在入库前已推进，所以入库失败 / 超时 /
  预算用尽的那批图**不会**在下一轮被重新处理；`/x状态` 的计数与一次性日志会如实记录这件事。
  `/x补发` 是诊断/回放动作（明确"不污染水位与投递记录"），**不写图库** ——
  否则一个测试动作会产生意外的归档副作用。需要补归档时，请在图库侧用 `/加图` 手动收录。
- **订阅规模很大时 WebUI 总览会慢**（既有问题）：实测 1200 条订阅下
  `web_overview_payload` 约 16 s，其中约 5 s 是逐 umo 开新连接查队列深度。
  机器人指令 `/x状态` 不受影响（约 60 ms）。

### v1.3.3 —— 修掉"连续 404 就把健康源熔断"的自锁

- **最严重**：v1.3.2 把"连续 N 次 404"直接当成"源坏了"，于是只要有 3 个账号被删/改名/打错（默认配置），
  健康的首选源就会被判定熔断，并被压到队尾再也回不来 —— 所有账号长期改走备用源，而该源的网络失败次数其实是 0。
  现在 404 只记 `not_found`：连续 404 达阈值后先用 `probe_handle` 探一次源本身，探针正常就清零、探针也失败才冷却。
- **`media_mode=download` 从这一版起才真正生效**：v1.3.0–v1.3.2 那句判断恒假，图片一直在走直链。
  升级后请留意 `media/` 目录增长与 `cache_quota_mb`。
- `/x源 <源名>` 的临时指定**只对下一次轮询生效**，订阅解析与回放既不消费它、也不按它的顺序抓取。

### v1.3.2 —— 修 v1.3.1 修出来的漏推

- **RSS 面的多个 URL 是备选入口**：某个面"合法但为空"时必须继续试后面的面，否则空面会遮住有内容的面，
  造成**永久漏推**。
- 「200 但解析不出来」一律判**该源不可用**，绝不伪装成"没有新帖"；FxTwitter 的「200 + 空 results 且无 cursor」
  同理（真信号是 204）。
- 只有**真的出了条目**的面才会被记成"下次首选"。

### v1.3.1 —— 首轮审查后的修复

- **一次 404 不再熔断健康源**：以前 `/x订阅` 打错一个 handle 就会把首选源冷却 600 秒、让所有账号改走 RSS。
- **链接不再指错**：`build_share_url` 优先用源给的 `url`；条目作者以 `<link>` 为准（`dc:creator` 只兜底）。
- 404 只记为 `not_found`，不灌进熔断计数；跨配置重建链路时只继承同配置 provider 的统计。

### v1.3.0 —— 多源降级链（L1 → L2 → L3）

- 抓取层抽象为 `FetchProvider` + `ProviderChain`：**L1** FxTwitter V2 API（地址可配）→
  **L2** `fxtwitter_rss`（通用 RSS/Atom 防御式解析 + XML 容错）→
  **L3** `rsshub`（自建 RSSHub / Nitter 实例池，逐实例故障转移 + 10 分钟实例冷却）。
- 新增配置 `fetch_chain` / `fxtwitter_api_base` / `rss_base` / `rsshub_instances` /
  `provider_failover_threshold` / `provider_cooldown_sec` / `probe_handle`，全部即时生效。
- `/x源`（仅全局管理员）列各源健康、主动探测、临时指定源；`/x状态` 与 WebUI 账号表显示生效源。

### v1.2.0
